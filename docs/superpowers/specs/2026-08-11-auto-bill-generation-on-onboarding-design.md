# Automatic transport bill generation for newly-onboarded learners

**Date:** 2026-08-11
**Status:** Design approved, implementation not started
**Supersedes:** `docs/superpowers/specs/2026-07-22-auto-bill-generation-design.md` (PR #12, branch `feat/auto-bill-generation`) — see "Why PR #12 is not merged" below.

## Problem

Transport bills are generated by hand. An admin opens a fee structure and clicks
Generate; the engine bills whoever is applicable and not yet billed.

Because learners join the transport cohort continuously, someone must keep
clicking. Measured over the 21 days to 2026-08-11: **30 generation runs, 100% of
them manual** (`tms_fee_generation_run.triggered_by IS NOT NULL`). On 2026-08-11
alone there were **eight** runs — 04:40, 04:41, 06:06, 06:22, 06:24, 06:41,
06:52, 07:04. The 07:04 run billed **1 learner and skipped 855**.

The lag between a learner becoming billable and a human noticing is 2–12
minutes of somebody watching a screen. That is the process being replaced.

## The event we cannot observe

The request was phrased as "once a learner onboards, generate the bill". The
onboarding event is **not observable from this codebase**.

A learner becomes billable when they satisfy the applicability predicate in
`lib/fees/applicability.ts`:

```
bus_required = true
AND lifecycle_status IN (structure.lifecycle_statuses, default ['active'])
AND institution_id IN (structure.institution_ids, empty = any)
```

Two facts follow from the live system:

1. **TMS-ADMIN never writes `bus_required`.** Every one of the ~60 references in
   the repository is a read filter or a type declaration. The flip happens in
   MyJKKN, a different application sharing the database. Evidence: learners
   billed on 2026-08-11 have `learners_profiles.created_at` months earlier
   (2025-07-27, 2026-01-03, 2026-03-08) but `updated_at` 2–12 minutes before
   their first bill — existing rows being flipped elsewhere.

2. **Route allocation is not part of the predicate.** Of 15 recently-billed
   learners, 2 had no `transport_route_id` at all. Hooking the Transport
   Enrollment `PATCH` (`app/api/admin/enrollment-requests/route.ts`) would be
   both unnecessary (billing does not need a route) and insufficient (it misses
   every learner flipped in MyJKKN without a TMS allocation).

There is therefore no in-application event to trigger on.

### Consequence: convergent, not event-driven

The engine already computes "who is applicable and not yet billed" on every run,
and `tms_fee_bill_idem_unique (fee_structure_id, person_id, term_no,
transport_year_id)` makes re-running harmless at the database level.

So the design is **not** change detection. It is running the existing idempotent
sweep on a schedule that fires. A missed run costs latency, never correctness.

## Institution-wise matching is already solved

Verified 2026-08-11 against live data: all **1,143** bus-required active
learners match **exactly one** active student fee structure — no gaps, no
overlaps, across all 8 institutions. The "check the institution-wise fee
structure" half of the request needs no new logic; `resolveApplicablePeople`
already performs it.

## Scheduling: why pg_cron, not Vercel

**Vercel crons have never fired in this project.** `vercel.json` schedules
`/api/cron/incharge-attendance` and `/api/cron/booking-reminders`. As of
2026-08-11, `tms_incharge_attendance_strike` has 0 rows and `tms_notification`
has 0 rows of category `booking` — after 3+ weeks. Neither job has ever run its
loop body.

**Root cause (identified in this design, correcting the earlier diagnosis):**
`proxy.ts` uses matcher `'/((?!_next/static|...).*)'`, which matches `/api/cron/*`.
`/api/cron/` is absent from both `PUBLIC_PATHS` and `PUBLIC_PATH_PREFIXES`. A
cron request carries `Authorization: Bearer <secret>` and **no Supabase session
cookie**, so `supabase.auth.getUser()` fails and `proxy.ts:88-91` returns 401
**before the route's own `CRON_SECRET` check ever executes**. The earlier note
attributing dormancy to an unset `CRON_SECRET` was wrong; the proxy blocks the
request at the edge.

**pg_cron is alive.** Verified 2026-08-11: `pg_cron 1.6` with 22 active jobs,
several on `*/5` and `*/15` schedules, most recent success 07:15 the same day.
`pg_net 0.10.0` performs outbound HTTP successfully (41 responses with status
201). Secrets are held in `vault.decrypted_secrets`, an established convention
in this database. MyJKKN already runs `jobid 19`,
`admission-reconcile-fee-events`, hourly — the same shape as this design.

## Architecture

Three layers.

```
pg_cron  '*/15 * * * *'
  └─ net.http_get(<app>/api/cron/auto-generate-bills,
                  Authorization: Bearer <vault secret>)
       └─ proxy.ts — exact-path allowlist ──────► forwards
            └─ route.ts — CRON_SECRET check (fail-closed)
                 └─ autoGenerateBills(svc)                 lib/fees/auto-generate.ts   NEW
                      ├─ settings toggle off? ─► skip
                      ├─ no current transport year? ─► skip
                      └─ structures WHERE active AND auto_generate AND year=current
                           └─ generateBills(svc, opts)     lib/fees/generate.ts        EXTRACTED
                                ├─ resolveApplicablePeople  ← institution-wise match
                                ├─ resolvePersonTerms       ← flat / tiered / stop_wise + overrides
                                ├─ skip already-billed      ← idempotent
                                └─ INSERT billing_student_bills + tms_fee_bill
```

### Layer 1 — `lib/fees/generate.ts` (extraction)

`app/api/admin/fees/[id]/generate/route.ts` is 763 lines containing applicability
resolution, term resolution, override loading, in-charge exemption, conflict
detection, bill insertion, staff notification and run logging — all coupled to
`NextRequest` and `AuthContext`, so nothing else can call it.

Extract to:

```ts
export interface GenerateOptions {
  feeStructureId: string;
  mode: 'dry_run' | 'generate';
  personIds?: string[] | null;
  actorId: string | null;        // null marks an automated run
  skipConflicts?: boolean;       // auto-only, default false
  skipEmptyRun?: boolean;        // auto-only, default false
}

export type GenerateResult =
  | { ok: false; status: number; error: string }
  | { ok: true; data: GeneratePreview | GenerateOutcome };

export async function generateBills(
  svc: SupabaseClient,
  opts: GenerateOptions
): Promise<GenerateResult>;
```

The route retains only: permission check (`TMS_PERMISSIONS.FEES_GENERATE`), id
extraction from the path, the empty-`personIds` rejection, `logActivity`, and
HTTP response shaping.

**This extraction must not change behaviour.** The defaults of `skipConflicts`
and `skipEmptyRun` are `false`, which is exactly what the route does today.

### Layer 2 — `lib/fees/auto-generate.ts` (new)

```ts
export interface AutoRunSummary {
  skipped?: 'disabled' | 'no_current_transport_year';
  structures: Array<{
    id: string; name: string;
    billed: number; skipped: number; unresolved: number;
    conflictsSkipped: number; bornOverdue: number;
    error?: string;
  }>;
  totalBilled: number;
  totalBornOverdue: number;
}

export async function autoGenerateBills(
  svc: SupabaseClient,
  opts: { dryRun?: boolean }
): Promise<AutoRunSummary>;
```

Sweep predicate:

```
tms_fee_structure
WHERE status = 'active'
  AND auto_generate = true
  AND transport_year_id = (SELECT id FROM tms_transport_year WHERE is_current LIMIT 1)
```

`dryRun: true` passes `mode: 'dry_run'` to every `generateBills` call, so the
sweep reports exactly what it would bill and writes nothing — no bills, no run
rows, no activity log entry. It is the safe probe used for verification.

A structure that errors is recorded in its own `structures[]` entry and the
sweep continues — one institution's failure must not block the others.

**The `auto_generate` flag is the only exclusion mechanism.** There is no
hardcoded structure-id or name blocklist: ids change when a structure is
recreated and names change when they are edited, so a hardcoded guard would rot
silently and give false confidence. Testing and Staff are excluded solely
because their flag is `false`, and the Phase 3 migration re-asserts `false` for
both idempotently so the intent is recorded in version control.

### Layer 3 — `app/api/cron/auto-generate-bills/route.ts` (new)

Mirrors `app/api/cron/booking-reminders/route.ts` exactly: `GET`, fail-closed on
missing or mismatched `CRON_SECRET`, `?dryRun=1` supported, `export const
dynamic = 'force-dynamic'`.

`GET` rather than `POST` deliberately: Vercel crons issue `GET`, so the endpoint
stays portable if that infrastructure is later repaired.

## Safety rails

| # | Rail | Mechanism | Prevents |
|---|---|---|---|
| 1 | Idempotency | `tms_fee_bill_idem_unique` (exists) | Double-billing — physically impossible |
| 2 | Global kill switch | `autoGenerateBills` in `admin_settings` scheduling blob, default **false** | Runaway automation |
| 3 | Per-structure opt-in | `tms_fee_structure.auto_generate` (column exists) | Testing / Staff auto-billing |
| 4 | Conflict skip | `skipConflicts: true` in auto mode | Billing someone another structure already billed |
| 5 | Fail-loud overrides | Existing engine behaviour | Overcharging a scholarship learner |

## Auto-only policies

1. **`skipConflicts: true`** — a person already billed by another structure for
   the same transport year is skipped and counted, never billed twice. Currently
   0 such people; this is insurance, not an active path.
2. **`skipEmptyRun: true`** — no `tms_fee_generation_run` row is written when
   nothing was billed. Without this, 96 runs/day across 3 structures would add
   ~288 empty rows daily.
3. **`actorId: null`** — distinguishes automated runs from the ~30 existing
   manual rows in `tms_fee_generation_run`.
4. **Born-overdue counting** — see below.

## Due-date policy: bill verbatim, report loudly

Term 1 is due 2026-07-31. All 12 Term-1 bills created on 2026-08-11 carry that
date, i.e. they were **overdue at the moment of creation**. Combined with the
fail-closed Term-1 access gate (shipped 2026-08-10), a newly-billed learner is
locked out of the student portal until they pay.

**Decision: do not alter due dates.** The structure's configured `due_date` is
copied verbatim, exactly as the manual path does today. Rationale: due dates are
snapshots written into *both* `billing_student_bills` and `tms_fee_bill`, and
TMS and MyJKKN must agree on them. Automation must not silently introduce a
second due date for the same term.

**Instead, count and surface it.** Every bill created with `due_date <
CURRENT_DATE` increments a `bornOverdue` counter, reported in the run notes, the
endpoint response, and the activity-log entry.

## Closing the orphan race

The engine inserts `billing_student_bills` (the real money row) and then
`tms_fee_bill` (the ledger row):

```ts
const { data: bill, error: billErr } = await svc.from('billing_student_bills').insert(...)
if (billErr || !bill) { errors++; continue; }
const { error: ledErr } = await svc.from('tms_fee_bill').insert(...)
if (ledErr) { errors++; continue; }   // <-- money row already committed, now orphaned
```

If the ledger insert fails, the money row is orphaned: MyJKKN shows a bill that
TMS does not know about, breaking the `Billed == Collected + Pending`
reconciliation invariant.

Verified 2026-08-11: **0 orphans exist today**, because manual runs are
serialised by a human clicking one at a time. A 15-minute cadence overlapping a
manual click makes the race reachable.

**Fix:** on ledger-insert failure, delete the just-created
`billing_student_bills` row before counting the error. This is a compensating
write that also benefits the manual path.

## Observability

`tms_fee_generation_run` is **write-only** — no UI reads it (verified: the table
name appears only in the generate route and `lib/fees/staff-bill.ts`).

Add a third exported variant to `lib/activity/log.ts`:

```ts
export async function logSystemActivity(entry: ActivityEntry): Promise<void>;
```

`tms_activity_log.actor_id` is nullable and `insertLog` already accepts
`{ id: null }`, so this needs no schema change. It writes `module: 'fees',
action: 'generate'` — both of which are **already members of the closed unions**
in `lib/activity/log.ts:13,19` and already rendered by the Activity Log page
(`activity-log/columns.tsx:47` action badge, `:66` module label). Automated runs
therefore become visible with **no union extension and no new UI**.

Note: `logSystemActivity` takes no `NextRequest`, so `ip_address` / `user_agent`
are null for automated entries. `insertLog` must be refactored to accept
optional client info rather than a required request.

## Proxy allowlist: exact path only

`proxy.ts` must allowlist the cron endpoint or the request 401s at the edge.

**Allowlist the exact path `/api/cron/auto-generate-bills`, NOT the
`/api/cron/` prefix** (which is what PR #12 did).

Allowlisting the prefix would simultaneously un-block
`/api/cron/incharge-attendance`, which after two consecutive missed travel days
**removes bus in-charges from their role and generates transport fee bills for
them**. Those two crons have been dormant since inception; waking them is a
separate decision with real consequences for 98 in-charges and must not be a
side effect of this change.

Implementation: add to `PUBLIC_PATHS` (the exact-match `Set`), not
`PUBLIC_PATH_PREFIXES`. Security is preserved by the route's own fail-closed
`CRON_SECRET` check.

## Settings

Add `autoGenerateBills: boolean` (default `false`) to `SchedulingConfig` in
`lib/settings/scheduling.ts`, parsed via the existing `boolOr` helper, plus a
toggle in the Settings → Scheduling tab.

The key is currently **absent** from the live `admin_settings` scheduling blob
(`{"bookingDaysAhead":1,"autoNotifyPassengers":true,"bookingWindowEndHour":19,
"enableBookingTimeWindow":true}`), so it parses to `false` — the sweep is inert
until deliberately enabled.

## Scope

Structures that will auto-generate (per approval 2026-08-11):

| Structure | Mode | Learners | `auto_generate` | Action |
|---|---|---|---|---|
| Transport Fees 2026-2027 | flat | ~697 | `true` | none |
| Transport Fees 2026-2027 (Arts Self) | tiered | ~432 | `true` | none |
| Transport Fees 2026-2027 (Arts Aided) | stop_wise | ~12 | `false` | **set `true`** |
| Testing | flat | 1 | `false` | **must stay `false`** |
| Transport Fees (Staff - All Colleges) | stop_wise | ~26 billable | `false` | **must stay `false`** |

Staff is excluded because that structure has **never been generated** (0 ledger
rows). Enabling it would create ~26 bills and fire ~26 notifications on the
first run. It should be generated by hand once, deliberately, before automation
is considered.

## Testing

**Characterization tests first, before the extraction.** The engine handles
money; the extraction must be provably behaviour-preserving.

1. Characterization tests over `generateBills` in `dry_run` mode against a
   mocked Supabase client, covering flat, tiered and stop_wise, with and without
   per-person overrides, pinning the exact `preview` object.
2. Sweep predicate unit tests: Testing excluded, staff excluded, inactive
   structures excluded, non-current transport year excluded.
3. Born-overdue counting: a term due yesterday counts, one due tomorrow does not.
4. Empty-run skip: `skipEmptyRun` writes no run row when `toGenerate === 0`;
   default `false` still writes one.
5. Orphan compensation: ledger-insert failure deletes the money row.
6. Live `?dryRun=1` probe confirming the sweep sees exactly the learners a manual
   run would.

Existing pure-logic tests (`resolve-terms`, `overrides`, `stop-rate`,
`person-scope`, `incharge-exemption`, `staff-bill`, `bills`,
`bill-analytics`) must continue to pass untouched.

## Phasing

| Phase | Content | Independently mergeable |
|---|---|---|
| 1 | Characterization tests + engine extraction + orphan fix | Yes — no behaviour change |
| 2 | Sweep, endpoint, proxy allowlist, settings toggle, `logSystemActivity` | Yes — inert while toggle is off |
| 3 | pg_cron schedule, Arts Aided flag on, global toggle on | Go-live |

Phase 3 requires operator steps that cannot be committed: storing `CRON_SECRET`
in `vault.decrypted_secrets`, setting the same value in the deployment
environment, and confirming the deployed application URL.

## Why PR #12 is not merged

Branch `feat/auto-bill-generation` is **86 commits behind main**. Its extracted
`lib/fees/generate.ts` was taken from a version of the route that predates:
per-student fee overrides (`lib/fees/overrides.ts`), stop-wise fee mode, real
staff billing (`lib/fees/staff-bill.ts`), staff notifications, and
`intersectPersonIds` scoping.

Merging it would regress the generator — most seriously, it would drop override
handling and overcharge scholarship learners. The engine must be re-extracted
from current `main`.

Its design remains sound in two respects, both retained here: the per-structure
`auto_generate` flag (whose migration is already applied to the live database)
and the global settings toggle.

## Out of scope

- Merging PR #12 or reviving `feat/auto-bill-generation`.
- Enabling staff auto-billing.
- Changing any due date, or back-dating/forward-dating existing bills.
- Hooking `app/api/admin/enrollment-requests/route.ts`.
- Repairing `/api/cron/incharge-attendance` and `/api/cron/booking-reminders`
  (root cause is documented above; the fix is a separate, deliberate change).
- Any UI for browsing generation-run history.
